The editable files

PistonCore's compiler keeps its knowledge in data files rather than buried in the program. That's what makes it repairable by whoever is using it — including after there's nobody maintaining it. This page is the reference for which file holds what, so a change lands in the right place.

They all live in customize/ on PistonCore's data folder. Editing one takes effect on the next compile — no rebuild, no restart. Your changes survive updates, and you can undo any of it from Settings → Translation data. How updates and restoring work →

You are not expected to hand-write these. The intended way is to describe the problem to an AI and let it make the edit — see extending the compiler with an AI. This page exists so you (or it) can tell which file is the right one.

The short version

If the problem is…Edit
Home Assistant renamed a service or a field, or a command does nothing / the wrong thing webcore_vocab.json
A state or value comes out wrong — "open" vs "on", an alarm mode, a fan speed, a colour name value_maps.json
A device doesn't show up, or shows up missing something it can do picker_capability_map.json
A piston is using PyScript when it shouldn't have to (or the reverse) routing_table.json
The generated automation is shaped wrong, or a webCoRE function is missing the .j2 template files

webcore_vocab.json — the translation

The big one, and the one that gets edited most. It holds webCoRE's entire vocabulary — every command, attribute and capability — and, against each one, the Home Assistant name it translates to.

Two halves, and the difference matters. The webCoRE half is frozen: webCoRE is finished software, its words never change, so those must not be edited. The "ha" entries beside them are the editable half, because Home Assistant renames things regularly. That's the whole design — the frozen word is a stable handle to look up the changing one.

An entry says which service to call and which fields to fill in, for example "turn on a light" → light.turn_on. Where a command isn't aimed at a device you picked — waking a PC over the network, setting location mode — the entry simply has no domain. There's also a small _ha_names section at the bottom for names that have no webCoRE counterpart at all, because webCoRE never had to do that thing.

Every HA name the compiler uses is in this one file. If you're hunting for a service name somewhere else, it isn't there.

value_maps.json — what values mean

Names versus values. The vocab says a lock is operated with lock.lock; this file says webCoRE's "unlocked" is HA's unlocked, that the opposite of "open" is "closed", which service arms an alarm to a given mode, and what "low" means as a fan speed.

Edit this when a piston triggers at the wrong time, or a mode lands on the wrong setting, even though the right service is clearly being called.

picker_capability_map.json — what your devices can do

Home Assistant describes a device with a domain, a device class, and a set of supported features. webCoRE describes it with capabilities and attributes. This file is the bridge, and it decides what you see in the device picker and which attributes each device offers.

Edit it when a device is missing from the picker, or is there but doesn't offer something it can plainly do.

routing_table.json — which engine a piston uses

PistonCore compiles to plain Home Assistant automations wherever it can, and falls back to PyScript for the things YAML genuinely can't express. This file is the list of what forces that fallback.

It's deliberately separate from translation, because it's the part that moves: every time Home Assistant gains an ability, something can come off this list and compile natively instead. Editing it changes which engine is used, never what the piston means.

The .j2 template files — the shape of the output

These decide how the finished automation is written out: the layout of the YAML, or the structure of the PyScript. The translation supplies the names; these decide the arrangement.

expr_runtime.py.j2 is the odd one out and worth knowing about: it holds webCoRE's functions — the maths, text and date helpers pistons can call. A missing function gets added there.

Templates are the risky ones. They're closer to program code than to data, and they run as part of your compiler. Editing your own is fine; importing one from a source you don't trust means running someone else's code. PistonCore warns you when an import includes a template, and lets you decide.

How to tell you got it right

Recompile a piston and look at the result. The compiler reads these files fresh every time, so there's no restart step and no waiting. If an edit makes things worse, Go back in Settings restores what was there before.
