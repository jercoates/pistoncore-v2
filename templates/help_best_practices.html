Getting started with PistonCore

PistonCore gives you the real webCoRE editor on top of Home Assistant. You write pistons exactly the way you always have; PistonCore turns each saved piston into native Home Assistant automations. This page covers the habits that make that go smoothly.

Where things live

The front door (PistonCore's own list) is home base: every piston, its compile status, whether it's running. Clicking a piston opens the webCoRE editor — the same editor, unchanged — and leaving it brings you back. Import/Export and Settings are PistonCore pages; everything piston-shaped is webCoRE's.

Bringing pistons in

  1. Set up your global variables first. A piston that uses @Speakers or similar refers to it by name only — the devices live in your instance, not in the piston. Create the globals with the same names (they're case-sensitive) and assign devices before compiling, or the piston will report the missing global.
  2. Import through the Import page (paste JSON) or the + New Piston dialog (restore code, backup file, duplicate). Either way webCoRE's own device-matching step runs, so imported pistons bind to your real devices — usually automatically, by name.
  3. Save once, then check the front door. Compiling happens on save; the status pill tells you what happened.

What the status pills mean

PillMeaning
deployed Live in Home Assistant and verified present after the reload.
compile error Something in the piston can't be built yet, or a device/global is missing. The message names the exact statement — and your piston is safe; the previously working version keeps running.
paused You paused it; its automation is disabled in HA.

Full detail, and what to collect when something goes wrong: Debugging a bad compile.

Install PyScript — recommended

Simple pistons become ordinary HA automations. Anything richer — formulas, switch, loops, variables, event blocks, computed notification or speech text — compiles to PyScript instead. Without the PyScript integration those pistons will report that they need it. Install it once from HACS (search “pyscript”) and every kind of piston can run. PistonCore tells you which band each piston used.

Writing pistons that compile well

These are habits in the webCoRE editor, not PistonCore settings. None of them is required — pistons written any other way still compile — but each one makes the result easier to read, easier to change later, and easier for PistonCore to understand correctly.

Declare your devices in define, then use the name

In the editor's define block, give a device (or a group of them) a name, and refer to that name everywhere in the piston instead of picking the device again in each statement. 

define
    device Water_Sensors_Always = Kitchen Leak, Water Heater Leak;
end define;

Why it pays off: when you replace a sensor, you change it in one place rather than hunting through every statement that mentioned it. It also makes the piston readable — "any of Water_Sensors_Always is wet" says what you meant, while a bare list of device names says only what you clicked. PistonCore reads those names too: it can tell that a statement naming the group and a statement naming one of its members are talking about the same devices, which helps it see that both belong to the same job.

Use globals for lists you reuse across pistons

A global device list (@Speakers, @Notifications_Push, @Presence_Sensor_All) lives outside any one piston, so every piston that uses it picks up a change at once. Add a speaker to the global, and every announcement in the house reaches it — no editing piston by piston.

You can also target more than one global in a single command. A notification sent to a text list and a push list together reaches both, with no second statement.

Worth knowing: whether a notification arrives as a text or a push is a property of the device you send it to, not of the command. "Send device notification" does whatever the target device does.

Write your statements in the order you want them to matter

PistonCore keeps the order you wrote things in. It never reorders your statements to make them easier to compile, and it never assumes two things are interchangeable just because it can't see a reason they aren't.

So put the thing that must happen first. In a leak piston, shutting the water off matters more than announcing it; if a speaker is offline or a notification service is down, you still want the valve closed. Ordering by what matters most costs you nothing and protects you when something in the chain fails.

Order also records how you think the piston fits together, and that survives into the compiled automation and its comments — which is what makes it readable in six months, by you or by whoever inherits it.

One piston, one job — where you can

A piston that does one thing is easier to pause, test, fix and reason about than one that does five. Pistons that stack several unrelated jobs still work, but every problem in them is harder to isolate, and the compiled output has more moving parts.

Deeply nested pistons — loops inside loops, work hung off several layers of condition — are compiled to PyScript rather than YAML, because PyScript can keep the structure intact. That is a normal outcome, not a failure.

Habits that keep things predictable

  • Pause instead of deleting while experimenting — pausing disables the automation in HA and keeps its history; enabling recompiles it fresh.
  • Let PistonCore own its files. Everything under pistoncore/automations/ and pyscript/scripts/pistoncore/ is regenerated on every save — edit the piston, never the generated file.
  • Rename freely. Renaming a piston moves its compiled file cleanly; no orphans left behind.
  • Use Home Assistant's own traces when a piston runs but does the wrong thing: Settings → Automations → your piston → Traces shows the exact path it took.
  • Keep credentials current. If you regenerate your HA token, update it in Settings — the front door's health badge is the fastest way to spot a broken connection.

If you get stuck

Every compile keeps its output. The three things that make any problem diagnosable — the piston's exported JSON, the newest file in its compile_debug folder, and the banner message — are described in Debugging a bad compile. You can re-run setup any time from Settings.
