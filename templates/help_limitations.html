Where Home Assistant differs from webCoRE

Almost everything in a piston survives the trip to Home Assistant unchanged. A few things can't, because HA has no equivalent for what webCoRE did. This page is the honest list — what you asked for, what actually happens, and what to do about it.

None of these are faults in your piston. Each one is a deliberate, documented choice PistonCore made instead of pretending. If a piston behaves slightly differently, you should read it here first rather than discover it months later.

"This piston can't be paused"

A piston with no triggers isn't an automation. If nothing wakes your piston, HA treats it as a script — a sequence you run on demand. HA can switch an automation off; a script has no on/off state to switch.

What to do: give the target piston a trigger, or don't pause it. PistonCore refuses to compile pausePiston aimed at one of these rather than emitting something that quietly does nothing.

A piston compiled to PyScript can't be paused either

PyScript pistons are modules, not Home Assistant automations, so there's no automation for HA to switch off. This is the same wall as the one above, for a different reason — and it applies whichever band the pausing piston uses.

What to do: if a piston needs to be pausable, leave it on ordinary automations rather than forcing it to PyScript.

"Deploy the target piston first"

Pausing works by naming the target's automations, and those names don't exist until that piston has been compiled once. Deploy the piston you want to pause, then the piston that pauses it. After that, redeploy either in any order.

Why it can't just look it up later: Home Assistant picks an automation's internal id from its name, and changes it if two names collide. The id can't be worked out in advance — only read back once the automation exists.

"This piston wakes on every sensor update"

You used a remains… comparison — "remains below 50", "remains inside range". That means was already true and still is, so the piston has to see every change to know it. HA has no trigger for that; its closest one fires at the moment of crossing, which is the exact case "remains" excludes.

What PistonCore does: that statement gets its own automation, limited to one run per second, with skipped runs silenced so they don't fill your log. On a fast-reporting sensor that's the difference between one run a second and fifty.

Worth knowingWhat it means
Brief spikes If the value jumps past the threshold and back within that one second, PistonCore counts it as "remained" where webCoRE would have seen a crossing.
Other statements The rest of that piston no longer re-runs on this trigger's events. webCoRE re-ran every statement on every piston event; allowing that here would wake the whole piston on every sensor update.

What to do: if you can say what you want with stays… instead, do — it carries a duration, HA supports that directly, and none of the above applies. If you need "remains" and want it quieter or faster, the limit is a plain delay: at the end of that automation with a comment explaining it. Edit it there.

"This condition is false right after deploying"

You used a was… comparison — "was below 50 for ten minutes". PistonCore answers that by remembering when it became true. On a freshly deployed piston nothing has been remembered yet, so the answer stays false until the value next changes into that state.

What to do: nothing. It settles by itself the first time the value changes.

Why it doesn't just ask HA: Home Assistant tracks when an entity last changed, and that resets on every update. A fridge going 11° to 12° is still above 10, but the clock would restart — so "above 10 for ten minutes" would never add up and the condition would never fire. Remembering it separately is the only accurate way.

This errs on the safe side: it under-reports how long something has held, never over-reports. An alert fires late rather than falsely.

"Why are there two triggers for one condition?"

You asked for "50 or more" (or "or less"). HA's numeric triggers are strict — "above 50" does not fire at exactly 50 — so PistonCore adds a second trigger for the exact value.

Don't delete the second one. Without it, a sensor sitting exactly at your threshold never fires at all. That was a real bug: a food probe holding exactly at temperature triggered nothing.

"Why is my fade two actions?"

"Fade from 20% to 80% over two minutes" becomes: jump to 20%, then fade to 80%. HA can't take a starting value and an ending value in one call. The result is what you asked for — it just reads as two steps.

Not supported: fading a camera's infrared level. HA has no equivalent.

Timers anchored to sunrise or sunset

"Every day at sunrise", "at sunset", "at noon", "at midnight" all work, and so does an offset — "30 minutes before sunrise", "an hour after sunset". These follow the real sun times for your location and shift through the year on their own.

Not supported — two cases, and both tell you rather than guessing:

  • A sun time on a cycle longer than a day — "every 2 days at sunrise", "every week at sunset". A once-a-day sun time is fine; spacing it out over several days isn't something HA can express.
  • An offset that is worked out while the piston runs — such as "sunrise plus <a variable>". The offset has to be a fixed amount of time you type in. A fixed offset covers nearly every real use.

Setting hue or saturation on a light that's off

Home Assistant has no "set hue only" or "set saturation only" service — it takes hue and saturation together as a pair. PistonCore handles that for you by reading the light's current colour and keeping the half you didn't ask about, so "set hue to 120" on a soft pastel stays a soft pastel.

The one gap: a light that is off, or that has never been given a colour, has no current colour to read. In that case the missing half falls back to full saturation, hue zero.

What to do: nothing for a light that's on. If you're setting a colour on a light you're also turning on, use Set color and give both values — that's exact regardless.

Timing on a value that lives inside a device is less precise

Some readings are the device's own state (a switch is on) and some live inside it as a detail — a thermostat's current temperature, a lock's last user. Home Assistant timestamps the whole device, not each detail separately.

What happens: "has been X for ten minutes" on one of those inner values is measured from the last time anything about that device changed. A thermostat reporting its humidity restarts the clock on a question about its temperature.

What to do: nothing, for most pistons — it errs towards firing late, not falsely. Force PyScript if a piston depends on that timing being exact.

"My variable got cut off"

Any value PistonCore stores in a Home Assistant helper is capped at 255 characters. That's HA's limit on any entity's state, not a choice PistonCore made.

What to do: if the piston genuinely needs a longer value — a large response, a long message — force that piston to PyScript, which has no such cap.

When to force PyScript

Every piston can compile to PyScript instead of ordinary HA automations. PyScript is a single file PistonCore controls end to end, so several of the limits above simply don't exist there, and the trace detail is closer to what Hubitat and SmartThings gave you.

The trade-offs: PyScript is an add-on you have to install, and pistons compiled that way don't appear in Home Assistant's automation editor. Use it deliberately, for a piston that needs it — not as the default.

Something not listed here?

If a piston behaves differently and you can't find it above, that's worth reporting. Either it belongs on this page, or it's a real bug. The rule PistonCore works to is that any difference from webCoRE gets written down as fair warning, never silently accepted — so a missing entry is itself a problem.
