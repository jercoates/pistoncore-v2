# SESSION BRIEF — One Reader, One Writer

**Status:** approved by Jeremy 2026-08-01, not started.
**Supersedes:** patching silent-drop bugs one at a time. Do this BEFORE more compiler
fixes — the backlog items land twice until it is done.

**No deadline pressure.** Jeremy's safety pistons still run on Hubitat. His ruling:
*"fixing the root problem is better than running off half baked."*

---

## 1. The problem, plainly

Your piston is read by two separate pieces of code that don't know the same things, and
written out by two more that don't agree with each other.

That is why one bug keeps returning in different clothes:

| what was dropped | which reader knew about it |
|---|---|
| actions attached to a condition (`ts`/`fs`) | **neither** — 9 pistons, incl. the whole safety set |
| `$device` used as a value | Python transpiler learned it 2026-07-29; the Jinja one never did |
| `each` over a device-list variable (`lo.t == 'x'`) | **neither** — only surfaced once `ts`/`fs` compiled |
| restrictions (earlier session) | **neither**, on both bands *and* both output kinds |

Each was patched where it was spotted. The next feature lands in one half again.

### The two readers (VERIFIED)
- `shim/compiler/analyze.py` reads the piston and builds an IR — consumed by the YAML band.
- `shim/compiler/emit_pyscript.py` **ignores that IR entirely** and walks the raw piston
  JSON itself (`stmt.get("c")`, `stmt.get("s")`, …).

Proof from this session: fixing `ts`/`fs` required two independent edits, in
`analyze.py` and in `emit_pyscript.py`, because neither shares the other's reading.

### The two writers (VERIFIED, and it has already caused a wrong safety automation)
The rules for emitting HA code are hand-written twice — once for Python (PyScript band),
once for Jinja (YAML band). They disagree. webCoRE joins adjacent operands as text for
strings and multiplication for numbers (groovy :10700-10724). The Python side gets this
right; the Jinja side emitted **multiplication for a text message**, so a Carbon Monoxide
alert compiled to `0.0` instead of the detector list. That output was caught by reading
it, not by any test.

## 2. Jeremy's rule this must satisfy (2026-08-01)

> Anything that tracks **HA's moving target** — service names, template functions, how a
> value is read — must live in **templates/data** so a user can fix it when HA renames
> things. Anything not exposed to that churn may stay hard-coded.

Reason: the user must be able to repair their own compiler with nobody upstream
(`overlay_merge_relief_valve`, `pistoncore_user_maintainability_goal`).

### Audit against that rule, 2026-08-01
**Clean:** every HA *service* name comes from `webcore_vocab.json`. Automation and script
skeletons are templates (`templates/compiler/{yaml/classic,pyscript/2.x}/`, 2 files each).

**Violating:** the HA *template expressions* — every `{{ states('sensor.x') == 'on' }}`
and every value read — are Python string code:

| file | HA-facing expressions hard-coded |
|---|---|
| `shim/compiler/expression.py` | 22, **plus `_JINJA_FUNCS`** (109-entry webCoRE-function → HA-template table, line 619) |
| `shim/compiler/emit_yaml.py` | 17 |
| `shim/compiler/resolve.py` | 5 (`read_expr`) |
| `shim/compiler/emit_pyscript.py` | 1 |

Only the outer skeleton is templated; everything *inside* the automation is generated by
Python.

## 3. The work, in order

### Stage 1 — ONE READER
One reader reads the piston completely; **both** bands consume it. Delete the raw-JSON
walk in `emit_pyscript.py`.

Why first: after this, a feature is read once and is automatically available to both
bands. Today everything must be built twice and half the time the second time never
happens.

**Verification:** `test_compile_snapshots.py` must report **NO DRIFT** — all 84 pistons
byte-identical — except where a change is intended and reviewed. Run it before and after
every step, not just at the end.

**Risk, stated honestly:** this is the structural one; it touches how everything is read.
Go in steps, harness after each. Do not batch.

### Stage 2 — ONE WRITER
Move HA-expression emission out of Python and into the band template files, so the rule
exists once and is user-editable. Satisfies §2 and removes the two-copies drift that
caused the multiplication bug.

Start with the highest-churn, highest-damage piece: `_JINJA_FUNCS` and the condition/value
expressions. `read_expr` in `resolve.py` is the single funnel for value reads — good first
target.

### Stage 3 — PROVE IT, THEN CLEAR THE BACKLOG
Run `test_intent_probe.py` across the whole vocabulary (79 comparisons, 136 commands, 109
functions, 12 statement types, four paths). Its differential test is the guarantee:
**remove a piece of a piston, recompile, and if the output is unchanged that piece was
being ignored.**

Then fix what it lists (see `round_e_intent_probe_findings` memory for the measured set):
- boundary `=` lost in the `stays_*`/`remains_*` families
- the whole `was_*` family silently compiling as `is_*`
- **29 of 79 comparison operators fail on the PyScript band.** Jeremy's rule: PyScript is
  a user-selectable choice for Hubitat-grade trace fidelity, so it **must be total** — a
  piston failing there is a bug in the valve, never a missing feature.

## 4. Ground rules for whoever executes this

- **Run the snapshot harness FIRST**, before touching anything, so the starting point is
  measured rather than assumed.
- **Never let a piston deploy doing less than it says.** Silence is the actual bug. If a
  shape can't be compiled, raise — and note that routing to PyScript is NOT a safe
  fallback for anything PyScript also drops.
- **Corpus absence is never a reason to skip something** (`compiler_make_it_work_rule`).
  The corpus is Jeremy's own pistons; PistonCore is for everyone.
- **Verify operands from the vocab, never by hand.** Hand-guessed operands produced false
  results three times before the probe existed, and three more times during the Round E
  sweep itself.
- **Document every divergence** from webCoRE behaviour as a fair-warning trade-off
  (`document_behaviour_divergences`).

**Known divergence shipped:** webCoRE short-circuits and/or groups, so a condition it never
reaches never runs its attached actions. Each is evaluated independently here, so in
"A and B" with A false, B's attached actions still run. webCoRE disables that optimization
itself whenever a group holds triggers or nested groups, which covers the corpus cases.
Fold this into the user-facing limitations doc.
